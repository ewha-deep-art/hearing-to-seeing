## [3] 영화·장면 식별 → RAG 검색 🟡

**a. 제목 파싱** 🟢 — 유튜브 클립 제목은 정제가 필요하다 (LLM 1회).
```
"[4K] 기생충 명장면 모음 | 아들아 너는 계획이 다 있구나 #shorts"
        ↓
작품명 "기생충"  +  장면 힌트 "아들아 너는 계획이 다 있구나"
```
LLM 답의 신뢰도가 `MIN_CONFIDENCE` 미만이면 규칙 기반 정제(`clean_title()` — 괄호 태그·해시태그·
`4K`·`예고편` 류 제거)로 폴백한다. API 키가 없어도 규칙 기반 경로는 동작한다.

**b. 장면 특정** 🟡 — 클립 한정의 가장 큰 이점.
```
영화 전체    등장인물 20명  → 매핑 후보 20개
클립 한 장면  등장인물 3명   → 매핑 후보 3개
```
제목의 장면 힌트와 transcript 대사 앞부분(`transcript_excerpt()`)을 검색 프롬프트에 함께 넣어
장면을 좁힌다. 결과의 인물 목록은 **장면 등장 인물 → 주연 → 조연** 순으로 정렬된다.

**c. RAG 검색** 🟢 — **배우가 아니라 극중 인물** 정보를 찾는다.
- 등장인물 목록 + 호칭(aliases) + 성격·역할·관계 텍스트 + 외형·의상 묘사
- 프로필 사진(레퍼런스) 🔴 — 문서를 텍스트로만 읽으므로 현재는 항상 `null`. 나무위키의 캐릭터 포스터 이미지 추출은 후속 과제

구현은 **자체 검색기 + Gemini 무료 티어** 두 단계:
1. [`retrieve.py`](../src/hearing_to_seeing/knowledge/retrieve.py) — 한국어 위키백과 API 로 문서를 특정하고,
   **나무위키**(등장인물 절이 있는 유일한 출처)와 위키백과 본문을 받아 개요·줄거리·등장인물 절만 예산 안에서 잘라낸다.
   나무위키는 best-effort — 실패하면 위키백과만으로 진행한다. 모델 호출 없음.
2. [`characters.py`](../src/hearing_to_seeing/knowledge/characters.py) — 잘라낸 문서를 프롬프트에 넣고 JSON 스키마로
   인물표를 받는다 (1회). `sources` 는 모델이 본 문서 URL 그대로.

> Google 검색 그라운딩은 쓰지 않는다 — 무료 티어 키에서는 모든 모델에서 할당량 0(429)으로 확인됨.
> 기본 모델은 `gemini-3.6-flash`(호출당 약 30초). 한도(429)는 즉시, 수요 폭주(503)는 짧은 재시도 후
> `gemini-3.5-flash-lite`(호출당 약 3초) 로 폴백한다. `H2S_LLM_MODEL` 로 바꿀 수 있다.
결과는 중간 JSON의 `work` 블록([`WorkInfo`](../src/hearing_to_seeing/schema.py))에 저장되며,
**같은 transcript를 다시 처리할 때 `work` 가 있으면 검색을 건너뛴다** ([8] 재사용의 첫 구현).

> ⚠️ 인물 문서에 **의상 색 묘사는 거의 없다.** 성격·역할 위주이므로 색상 근거로는 약하며,
> 색의 1차 근거는 [4]e에서 화면에서 직접 얻는다. 그때까지는 [6]b가 문서의 의상 묘사를 1단계로 쓴다.

> 구현: [`knowledge/title.py`](../src/hearing_to_seeing/knowledge/title.py) (a),
> [`knowledge/characters.py`](../src/hearing_to_seeing/knowledge/characters.py) (b·c),
> [`knowledge/llm.py`](../src/hearing_to_seeing/knowledge/llm.py) (`LLM` 프로토콜 + Gemini 백엔드 — 스키마 고정 출력·
> 429/503 재시도와 모델 폴백·차단 처리; Claude 는 [`claude.py`](../src/hearing_to_seeing/knowledge/claude.py),
> `H2S_LLM_PROVIDER=claude`). CLI에서는 `--lookup` 으로 켠다 (`GEMINI_API_KEY` 필요).
> 이 플래그가 없으면 파이프라인은 네트워크에 아무것도 보내지 않는다.

## [4] 화자별 대표 증거자료 추출 🔴

**a. 후보 세그먼트 선정** — 길이 1.5초 이상, 화자 오버랩 없는 구간 우선

**b. 프레임 추출** — 각 후보의 중간 지점에서, 분석용 사본으로부터 얼굴 검출

**c. 얼굴 개수로 우선순위 분기**

| 얼굴 수 | 처리 |
|---|---|
| 1명 | ✅ 사진 채택 — 기본 케이스. 대부분 여기서 화자당 3~5개 확보 |
| 2명 | 두 얼굴만 남기기 |
| 3명 이상 | 후순위로 밀고 1~2명짜리 다른 세그먼트로 대체 |

**d. 얼굴 0명** (오프스크린 목소리 등) → 후보 제외, 다음 순위로 대체

**e. 의상 대표색 추출**
```
얼굴 박스  →  아래쪽 상체 영역 크롭  →  피부·배경 제외  →  대표색
```
- 상체 영역: 얼굴 박스 높이 기준 아래로 약 1~3배, 좌우 ±1배
- 피부색 제외, 배경은 중앙 가중치로 완화 (person segmentation은 후속 과제)
- LAB/OKLCH 공간에서 k-means → 최대 클러스터의 중심색
- **여러 후보 사진의 결과가 일치할수록 신뢰도 상승** (조명·장면 차이를 상쇄)
- ⚠️ **채도가 임계값 미만이면 "색 근거 없음"으로 표기한다.** 실사 영화는 무채색
  의상(검정·회색·남색 정장)이 흔하므로, 억지로 색을 뽑지 않고 [6]b의 2단계로 넘긴다

**[4]의 산출물은 두 곳에서 쓰인다:**
1. [5]b 비전 자동 대조의 입력
2. **[7] 확인 UI에서 사용자에게 보여줄 증거** ← 레퍼런스 사진 확보에 실패해도 이쪽은 유효

## [5] 화자 → 인물 매핑 🟡

**a. 텍스트 기반** 🟢 — 화자 대사 + RAG 인물 특징으로 후보 추론
- **호명 탐지(규칙 기반)로 앵커를 먼저 확보** — 인물 이름·호칭(`aliases`)이 대사에 나오면
  (조사가 붙은 "기택아", "사장님은"도 접두 매칭) 두 가지를 센다:
  말한 화자는 그 인물이 *아닐* 가능성이 높고, `REPLY_WINDOW`(4초) 안에 다음 턴을 받은 화자는
  그 인물*일* 가능성이 높다. 손으로 검증 가능한 카운트이며 LLM 프롬프트에 제약으로 들어간다.
- 그 위에서 LLM 1회 추론 — 인물표(역할·성격·관계·호칭) + 앵커 + 시간순 대사(앞부분은 전부,
  나머지는 균등 샘플링, `MAX_DIALOGUE_CHARS`) → 화자별 `{인물 | null, 신뢰도, 근거}`.
  확신이 없으면 null 로 두라고 지시한다 — 틀린 이름은 이름 없음보다 나쁘다.
- 존댓말 방향·가족 호칭·관계는 프롬프트 원칙으로 넣었고, 별도 규칙은 없다.
- 두 화자가 같은 인물로 추정되면 둘 다 이름을 유지하고 note에 "화자 병합 검토"를 남긴다
  (병합 자체는 [7]).

**b. 비전 기반** 🔴 — [4]의 얼굴 사진 vs RAG 레퍼런스 사진
- 1차: 얼굴 임베딩 유사도 (싸다)
- 2차: 애매한 경우만 비전 LLM으로 재확인 (비싸다)
- ⚠️ 애니메이션·분장이 심한 경우 임베딩이 작동하지 않는다. 레퍼런스 사진이 없으면 생략

**c. 결합** 🟡 — 현재는 전략 **겹치기**(`layered()`)만 있다: 수동 → 저장된 매핑 → 텍스트 추론
순으로, 앞 전략이 이름을 댄 화자는 뒤 전략에 묻지 않는다 (모두 채워지면 LLM 호출도 생략).
a + b 의 신뢰도 통합은 b 가 생기면 🔴

**d. 실패한 화자 처리** 🟢 — 단역·나레이션 등 주요 인물이 아닌 화자
- **저채도 그룹**으로 통일: `L 고정 · C 낮음 · Hue는 화자마다 다름`
- 주요 인물(고채도)과 구분되면서, 단역끼리도 서로 구분된다
- 신뢰도 미달로 기각된 이름은 `speaker_profiles[].note` 에 `discarded …` 로 남는다
- 흰색(`&H00FFFFFF`)은 생성되지 않는다 — 모든 화자 색은 채도를 가진다

> **수동 매핑** 🟢 — `--speaker-map "SPEAKER_00=기택,SPEAKER_01=충숙"`
> ([`identity.py`](../src/hearing_to_seeing/design/identity.py)).
> 자동 경로의 대체재가 아니라, 자동 결과를 교정하는 수단이자 정확도 측정의 정답지다.
>
> 텍스트 추론 🟢 — [`design/inference.py`](../src/hearing_to_seeing/design/inference.py)
> (`detect_anchors()`, `infer_from_text()`), `--lookup` 에 포함.
> 신뢰도 임계값 미만을 기각하고 폴백하는 로직 🟢
> ([`resolve_speakers()`](../src/hearing_to_seeing/design/speaker.py))

## [6] 색상 결정 🟡

### a. 색상 기준 🟢

```
색 = OKLCH(L 고정, C 최대, H 자유)
      L 고정 → 어떤 색을 골라도 가독성이 보장된다
      H 자유 → 팔레트 7색 제한이 사라진다

배정 = 선호 각도에 최대한 가깝게 + 화자 간 최소 각도 간격 강제
```

- **색맹 안전성은 고려하지 않는다** (표현력 우선). 필요하면 이후 별도 옵션으로 분리
- 주요 인물은 고채도, [5]d의 실패 화자는 저채도
- 매핑 실패·신뢰도 미달 화자에 대한 폴백은 반드시 존재해야 한다

> 구현 완료 🟢 — [`oklch.py`](../src/hearing_to_seeing/design/oklch.py)가 색공간을,
> [`assign_hues()`](../src/hearing_to_seeing/design/speaker.py)가 배치를 담당한다.
> 남은 것은 b(선호를 정하는 쪽)뿐이며, 선호가 하나도 없으면 색상환에 균등 배치된다.

### b. 색상 추출 근거 (인물당 1회 캐싱) 🟡

| 단계 | 근거 | 성격 | 상태 |
|---|---|---|---|
| 1단계 | **[4]e 의상 대표색** (화면 샘플) | 화면에 근거가 있어 **사용자가 즉시 검증 가능** | 🔴 |
| 1단계′ | [3]c 문서의 **의상 묘사** → 색 | 화면 샘플이 생기기 전까지의 대체 근거 (`costume`) | 🟢 |
| 2단계 | RAG 성격·역할 (1단계가 무채색이거나 실패 시) | 상징색 — 깊지만 검증 불가 (`symbolic`) | 🟢 |
| 실패 | 근거 없음 (`achromatic` / `none`) | a의 폴백으로 넘김 | 🟢 |

1단계를 앞에 두는 이유: 목표가 "누가 말하는지 즉시 인식"이므로,
**화면과 자막이 서로를 설명하는 색**이 상징적으로 깊은 색보다 낫다.

전략은 색을 확정하지 않는다 — **선호(선호 hue 각도 + 가중치)만 내놓고**, 확정은 a가 한다.

구현 방식: 작품의 전체 인물을 LLM에 **한 번에** 넘겨 인물마다 `costume`·`symbolic` 두 색을
sRGB hex로 받는다 (한 번에 묻는 이유 — 상징색이 인물끼리 겹치지 않게 고르도록). 단계 선택은
코드가 한다: hex → OKLCH 변환 후 **채도가 `ACHROMATIC_CHROMA`(0.06) 미만이면 무채색**으로 보고
다음 단계로 넘긴다 (검정·회색·흐린 남색 정장이 여기서 걸러진다). 결과 hue·근거·신뢰도는
[`Character`](../src/hearing_to_seeing/schema.py)의 `hue_*` 필드에 기록되어 중간 JSON에 남고,
이미 결정된 인물은 다시 묻지 않는다.

가중치(충돌 시 누가 선호를 지키는가) = 근거 가중치(costume 1.0 / symbolic 0.7) × 비중(주연 1.0 /
조연 0.6) × 신뢰도.

**화자와의 연결** — `with_character_hues()` 가 [5]의 identity 전략을 감싸, 전략이 이름을 댄 화자에게
그 인물의 hue 를 선호로 붙인다. 현재는 [5]의 수동 매핑(`--speaker-map`)만 있으므로
`--lookup --speaker-map "SPEAKER_00=기택"` 조합이 "인물 정보 → 색" 경로의 첫 end-to-end 다.
전략이 자체 hue 근거(화면 샘플 등)를 이미 갖고 있으면 그것을 우선한다.

> 구현: [`design/character_color.py`](../src/hearing_to_seeing/design/character_color.py)

## [7] 확인 UI 🔴

신뢰도에 따라 사용자 수고를 차등 적용한다.

| 신뢰도 | 처리 |
|---|---|
| 높음 | 가벼운 확인만 요청 |
| 중간·낮음 | 상세 검토 UI 노출 |

**상세 검토 화면**
```
[RAG 레퍼런스 사진 + 인물명]   vs   [영상 증거자료(사진/클립) + 추정 인물명]
```
- 인물명·색상 수정
- 화자 병합/분리 (diarization의 과분할·병합 오류 교정)

> 자동화가 전혀 없어도 [4]의 증거자료만 있으면 이 UI는 성립한다.
> 사용자가 사진을 보고 이름을 고르는 것만으로 매핑이 완성된다.

## [8] character_map 저장 🟢

확정된 매핑을 저장하고, **같은 영상을 다시 처리할 때 재사용**한다.

중간 JSON에 두 블록이 나뉘어 있다:

| 블록 | 성격 | 누가 읽는가 |
|---|---|---|
| `character_map` — `{"SPEAKER_00": "기택", …}` | **확정된 매핑**. 신뢰도 임계값을 넘은 이름만. 사람이 고쳐 쓰는 블록 | 다음 `from-json` 실행이 `stored` 전략으로 그대로 재생 (신뢰도 1.0) |
| `speaker_profiles` | 기계의 기록 — 색상·이름·신뢰도·출처(`manual`/`stored`/`text`/`unidentified`)·근거 | 사람이 검토용으로 읽음 |
| `work` | 작품·인물표·인물별 색상 근거 | 재실행 시 검색·색상 결정 생략 |

**교정 워크플로 (UI 이전의 [7] 대체):** `--json` 결과의 `character_map` 에서 틀린 이름을 고치거나
빠진 화자를 추가하고 `from-json` 으로 다시 돌리면, 그 매핑이 확정으로 채택되고 색상만 다시 배정된다.
`--fresh` 는 `work` 와 `character_map` 을 버리고 검색·추론을 처음부터 다시 한다.

> 영상 없이 [3]·[5]a·[6]b·[8]만 돌려 보려면 `hearing-to-seeing lookup <transcript.json>` — [4] 음량 단계를 건너뛰고
> `data/output/<이름>.lookup.json` 을 쓴다 ([`pipeline.run_lookup()`](../src/hearing_to_seeing/pipeline.py)).
>
> 구현: [`Transcript.character_map`](../src/hearing_to_seeing/schema.py),
> [`identity.stored_mapping()`](../src/hearing_to_seeing/design/identity.py),
> [`pipeline._finish()`](../src/hearing_to_seeing/pipeline.py)

## [9] 재생 🟡

## 구현 순서

| # | 작업 | 외부 의존 | 완료 시점의 상태 |
|---|---|---|---|
| **0** | 스키마 + 전략 계층 + 배정 🟢 | 없음 | 색상 결정을 갈아끼울 수 있는 토대 |
| **1** | [5] 수동 매핑 `--speaker-map` 🟢 | 없음 | **파이프라인이 끝까지 동작.** 평가셋 확보 |
| **2** | [6]a OKLCH 색상환 + [5]d 저채도 그룹 🟢 | 없음 | 팔레트 7색 제한 해제 |
| **3** | [4] 증거자료 추출 (+ 의상색) | 얼굴검출 | [7]에 보여줄 재료 확보 |
| **4** | [7] 확인 UI | 없음 | **실용 도구 완성** — 자동화 0%여도 쓸 만함 |
| **5** | [3] RAG 🟢 + [5]a 텍스트 추론 🟢 + [8] 저장·재사용 🟢 | LLM | 자동화 ~70% |
| **6** | [6]b 색상 추출 근거 🟢 (문서 기반; 화면 샘플 1단계는 [4] 이후) | LLM | 색에 의미가 생김 |
| **7** | [5]b 비전 대조 | LLM + 비전 | 자동화 ~85% |
| **8** | [9] 웹 플레이어 | 없음 | 원본 화질 재생 |

**4번까지가 외부 API 없이 도달 가능한 지점**이며, 그 자체로 완결된 도구다.
5번 이후는 "동작하게 만드는" 작업이 아니라 "사용자 수고를 줄이는" 작업이다.
5·6번([3], [5]a, [6]b, [8])은 3·4번보다 먼저 구현되었다 — 모두 `--lookup` 뒤에 있어 끄면 2번까지의
경로와 동일하게 동작하고, `--lookup` 을 켜면 **작품당 LLM 4회**(제목 파싱 → 인물 정리 → 색상 → 화자 매핑; 문서 검색은 모델 없이)로
`--speaker-map` 없이도 이름·색이 붙는다. 정확도는 [5]의 수동 매핑 정답지로 측정해야 한다.

### 선행 과제

**테스트 영상** — 3번부터는 실제 영상 없이 개발·검증이 불가능하다.
20분 내외 유튜브 영화 클립 1개를 `data/input/`에 두고, `uv sync`로 전체 의존성을 설치해야 한다.

**평가셋** — [5]의 정확도를 측정할 정답지가 없으면 개선 여부를 알 수 없다.
1번의 수동 매핑 결과가 그대로 평가셋이 된다.
