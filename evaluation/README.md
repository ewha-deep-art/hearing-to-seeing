# 전사·화자 평가

검수본(gold)과 파이프라인 결과(library)를 비교한다.
gold 파일과 library 결과는 전사 텍스트 유사도(rapidfuzz ratio ≥ 50)로 짝짓는다.

### 텍스트

- WER은 8~24%, CER은 3~17%다.
- 오류는 대부분 삭제(D)다. 삽입은 적고(IER ≤ 2.2%), 반복 루프도 없다. 즉 환각보다 누락이 문제다.
- 슬기로운 의사생활의 5-Dup 1건은 루프가 아니다. gold에도 같은 대사가 두 번 나온다.

### 화자

화자 정확도는 45~92%로 영상마다 차이가 크다. 실패 유형은 두 가지다.

- **쪼개짐**: gold 화자 한 명이 library 라벨 여러 개로 나뉜다. 검사외전과 마녀에서 일어났고, 해당 주연의 recall이 0.35~0.55로 떨어진다.
- **합쳐짐**: gold 화자 여러 명이 library 라벨 하나로 묶인다. 슬기로운 의사생활에서는 4명이 하나로 묶였고, 브레드이발소는 gold가 14명인데 library는 6명이다.

### macro F1

발화가 몇 단어뿐인 단역은 F1이 0이 되기 쉽고, 이것이 평균을 크게 끌어내린다. 화자 성능은 정확도와 함께 봐야 한다.

## 2. 지표 설명

공통 전처리: 문장부호를 지우고 공백 기준으로 단어를 나눈다.

### 텍스트

| 지표 | 의미 | 계산 |
|---|---|---|
| WER | 단어 오류율 (S + D + I) / N | `jiwer.process_words` |
| S / D / I / C | 치환 / 삭제 / 삽입 / 일치 단어 수 | 같은 정렬 결과 |
| CER | 글자 오류율. 한국어는 띄어쓰기 차이가 WER을 키우므로 함께 본다 | `jiwer.cer` |
| IER | 삽입 오류율 I / N. 환각으로 생긴 단어의 비율 | WER 성분에서 계산 |
| 5-Dup | library 전사에서 두 번 이상 나온 5-gram의 초과 등장 수. Whisper 반복 루프 탐지용 | `Counter` |

N은 gold 단어 수다. 모든 지표는 낮을수록 좋다.

### 화자

| 지표 | 의미 | 계산 |
|---|---|---|
| 화자 정확도 | 정렬된 단어 중 화자가 맞은 비율 | `sklearn.accuracy_score` |
| macro P / R / F1 | gold 화자별 precision / recall / F1의 단순 평균 | `sklearn.precision_recall_fscore_support` |
| JER | 화자별 발화 구간 Jaccard 오류의 평균 (시간 기준, 낮을수록 좋음) | `pyannote.metrics.JaccardErrorRate` |

- **단어 정렬**: WER 계산 때 jiwer가 만든 정렬을 그대로 쓴다. 일치(C)와 치환(S)으로 짝지어진 단어 쌍만 화자를 비교한다.
- **라벨 매핑**: library 라벨(`SPEAKER_xx`)과 gold 라벨은 이름이 서로 다르다. 그래서 두 라벨이 겹치는 단어 수 표(`sklearn` contingency matrix)를 만든다. 그다음 헝가리안 알고리즘(`scipy.linear_sum_assignment`)으로 일치 단어가 최대가 되도록 1:1 매핑한다. 짝을 못 찾은 library 라벨은 `<unmapped>`로 두고 오답으로 센다.
- **JER 구간**: 같은 화자의 단어 간격이 0.5초 이하면 한 발화로 합친다(`--merge-gap`). 경계 오차는 0.25초까지 무시한다(`--collar`).
- **JER 해석 주의**: JER은 단어 시간 정보에 의존한다. gold에는 검수 과정에서 늘어난 단어 구간이 있어서 수치가 높게 나온다. 예를 들어 부부의 세계의 총 발화 시간은 gold 333초, library 221초다. 영상끼리 상대 비교하는 용도로만 본다.

| 사랑과 전쟁 (gold 없음) | 873초 | 3 | – | – | 176.1·178.8초\* (GPU 메모리 부족 재시도 약 35초 포함) |
| 드라마 3·4회 요약 (gold 없음) | 900초 | 3 | – | – | **126.4초**\* |

- 이전 처리 시간은 웹 작업 기록(슬의)과 이전 파이프라인 측정(터널)이다.
- 서버 diarization은 검사외전 132초, 브레드이발소 73초가 걸려 15분 목표(3분 이내)를 넘겼다. 같은 클립도 실행마다 24~141초로 달라진다(LOG.md 6.1). 목소리 화자 분리는 4~17초(CPU)이고 나머지 패스와 겹쳐 돈다.
- \*는 Gemini 하루 한도가 다 차서 리뷰 없이 잰 시간이다. 리뷰는 첫 패스 뒤 나머지 패스와 겹쳐 돌고, 리뷰가 있던 실행에서는 모두 STT보다 먼저 끝났다. 브레드이발소는 리뷰가 한도 초과·과부하로 90초를 기다린 끝에 실패해 그만큼 늘었다.
- 15분 클립은 2~3분이다. 873초 클립은 첫 패스가 매번 서버 GPU 메모리 부족(503)으로 한 번 실패해 다시 올렸다(LOG.md 6.4).

정확도:

| | WER (평균) | 화자 Accuracy |
|---|---|---|
| 10-18 설정 (4.2절) | 0.155 | 0.932 |
| 현재, 서버 diarization (실행 1회씩) | **0.150** | 0.881 |
| 같은 모델 짝 비교 (공통 4개): 이전 방식 → 서버 라벨 → 목소리 라벨 | | 0.924 → 0.911 → 0.923 |

- WER은 패스 조합(5.8절)으로 6개 중 5개가 낮아졌다. 화자 분리 방식은 WER에 영향이 없다.
- 화자 정확도는 리뷰의 실행 간 편차가 크다(같은 방식으로 한 영상에서 0.75~0.92). 짝 비교는 `gemini-3.8-flash`, 캐시 입력, 목소리 보정 포함이고 영상별 값은 LOG.md 6.5·6.7에 있다. 목소리 라벨은 이전 방식과 0.01 안쪽이다.
- 리뷰 없는 경로의 화자 정확도는 서버 diarization 0.759 → 목소리 화자 분리 0.804다.

## 5. 적용한 변경

### 5.1 리뷰가 완주하도록 (`knowledge/llm.py`, `review.py`)

- **원인 1, 서버 데드라인**: google-genai는 첫 요청의 `X-Server-Timeout`(클라이언트 기본 180초)을 공유 헤더에 넣어 두고 다시 바꾸지 않는다. 그래서 리뷰에 준 타임아웃과 상관없이 서버가 180초에 끊었다(504 DEADLINE_EXCEEDED).
  - 수정: 요청마다 헤더를 명시한다.
- **원인 2, 시간 부족**: 590초 영상을 전체 thinking으로 검토하면 시간 안에 끝나지 않는다. low thinking으로 화자만 물어도 약 260초가 걸렸다. 과부하일 때는 10분을 붙잡고 있다가 실패한 적도 있다.
  - 단어 고르기는 전체 thinking이 필요하다. low에서는 클립 1에서 다수결을 52번 뒤집어 CER이 2.5 → 4.1%가 됐다. 화자는 low로도 99%가 맞는다.
  - 수정 1: 텍스트 검토(전체 thinking)는 측정된 범위인 300초 이하 클립에만 쓴다(`TEXT_MAX_SECONDS`). 더 긴 클립은 화자만 low thinking으로 묻는다. 5.8절에서 텍스트 검토를 껐다.
  - 수정 2: 타임아웃을 120초에서 480초로 늘렸다.
- **원인 3, 길이 제한**: 600초를 넘는 클립(부부의 세계, 브레드이발소, 마녀)은 리뷰 대상에서 빠졌다.
  - 수정: `MAX_SECONDS`를 900초로 늘렸다. 저해상도 영상은 초당 약 115 입력 토큰이라 컨텍스트에 여유가 있고, 답은 발화 수에 비례한다(12분에 약 250개). 측정한 가장 긴 클립은 12.3분이다.
- 호출 수는 그대로다. 클립마다 리뷰 1회 또는 대사 기반 추론 1회다.

### 5.2 저-VAD 패스 추가 (`stt.py`)

- large-v3 / chunk 30 패스 하나를 VAD onset 0.2 / offset 0.15로 추가했다(`LOW_VAD`). 서버 기본값은 0.5 / 0.363이다.
- 근거: 고함이나 속삭임 대사가 기본 VAD에 잘려 다섯 패스 모두에서 빠졌다. 예를 들어 터널의 마지막 대사는 어느 패스에도 없었다.
- 비용: 클립당 GPU 약 1분.

### 5.3 목소리로 화자 보정 (`voice.py`, 신규)

- 화자 임베딩 모델 WeSpeaker ResNet34(ONNX, 26MB)를 CPU에서 돌린다. 10분 영상에 약 6초 걸린다.
- 리뷰가 없을 때: 목소리 중심 유사도가 0.65 이상인 diarization 라벨을 합친다. 테스트 클립에서 diarization이 쪼갠 같은 사람은 0.61~0.71, 다른 사람은 최대 0.57(만화 캐스트 한 쌍만 0.62)이었다.
- 리뷰가 있을 때: 다른 화자 목소리에 0.15 이상 더 가까운 1초 이상 발화를 그 화자에게 옮긴다.
- 모델은 처음 쓸 때 내려받는다. 받지 못하면 라벨을 그대로 둔다.
- 새 의존성: `onnxruntime`, `kaldi-native-fbank`.

### 5.4 캐스트 문서 검색 (`knowledge/retrieve.py`, `pipeline.py`, `prompts.py`)

- 나무위키가 "X/등장인물 문서 참고"로 넘기면 하위 문서에서 인물별 섹션을 가져온다. 터널, 부부의 세계, 슬의가 이 경우다.
- 같은 이름의 문서가 여럿이면 클립 제목의 단어(배우 이름 등)가 가장 많이 나오는 문서를 고른다. 마녀는 서양 마녀 인물 대신 '마녀(드라마)'를 고른다.
- 문서가 없으면 나무위키 검색 결과 중 제목이 가장 가까운 문서를 쓴다. LLM이 '슬기로울'을 '슬기로운'으로 적은 경우가 이에 해당한다.
- 캐스트 프롬프트에 클립 제목을 넣고, 조연까지 최대 15명을 뽑게 했다. 같은 호출 1회 안에서 바꾼 것이다.
- 효과는 4.2절 리뷰 결과에 포함된다.

### 5.5 리뷰 모델과 예비 모델 (`review.py`, `knowledge/llm.py`)

- 리뷰는 `gemini-3.7-flash`로 묻는다. `gemini-3.5-flash` 요청은 캐스트 작성과 같은 `gemini-3.6-flash` 한도(하루 20회)로 집계되기 때문이다.
- 429·503이면 `gemini-3.8-flash`, `gemini-3.5-flash` 순서로 다시 묻는다. 모델마다 한도가 따로다. 리뷰가 성공하면 호출 수는 그대로다.
- 3.8은 측정 중 503이 두 번 연속 났고, 3.7은 8번 모두 응답했다.
- Lite 모델은 쓰지 않는다. 캐스트 작성에서 3.5 Flash Lite는 실제 화자(슬의의 금새벽·함동호 등)를 빠뜨렸다.

### 5.6 단역 구분 프롬프트 (`knowledge/prompts.py`)

- 캐스트에 없는 인물을 '손님1, 손님2'로 부르던 지시를, 생김새나 하는 일로 짧은 이름(간호사1, 경찰 등)을 붙이고 다른 사람끼리 같은 이름을 쓰지 않게 바꿨다. 이름 자체가 맞는지는 평가에 영향이 없다.

### 5.7 작품명 판별 호출 생략 (`knowledge/retrieve.py`, `pipeline.py`)

- 클립 제목을 구분자로 나눈 조각 중 정확히 하나가 나무위키 작품 문서(줄거리·등장인물 소제목이 있는 문서)의 이름이면, 작품명 판별 LLM 호출 없이 그 이름을 쓴다.
- 테스트 클립 7개 중 5개가 LLM 답과 같은 작품명으로 생략된다. 브레드이발소와 슬의는 LLM에 묻는다.
- 검색 결과로 찾는 방식은 쓰지 않는다. '브레드이발소2'를 '브레드이발소5'로 잘못 찾았다.
- `gemini-3.6-flash` 한도를 쓰는 호출이 클립당 2회(작품명, 캐스트)에서 대부분 1회(캐스트)로 준다. 리뷰는 `gemini-3.7-flash` 한도를 따로 쓴다(마지막 예비 `gemini-3.5-flash`만 3.6 한도로 집계).

### 5.8 처리 시간 단축 (`stt.py`, `review.py`, `pipeline.py`, `media.py`, `web/jobs.py`, `voice.py`)

목표는 5분 영상 1~2분, 15분 영상 2~3분이다. 실험 과정은 [LOG.md](LOG.md) 6절에 있다.

- **패스 6개 → 4개**: large-v3/30(diarization), large-v3/30 저-VAD, large-v2/30, large-v3-turbo/30. 6개 영상 모두에서 이전 6패스보다 WER이 낮다(평균 0.158 → 0.149). GPU 시간은 절반이다. chunk 5 패스가 가장 비쌌다.
- **10분 넘는 클립은 3패스**(`LONG_SECONDS`): large-v2를 빼 모델 전환도 한 번 준다. 평균 WER은 0.153으로 여전히 이전보다 낮다.
- **FLAC 업로드**: 패스마다 같은 오디오를 다시 올린다. FLAC은 무손실로 WAV의 절반 크기다. Opus(32k·64k)는 WER을 올려 쓰지 않는다.
- **목소리 화자 분리**(`voice.diarize`): 서버 diarization 대신 첫 패스를 목소리 임베딩으로 라벨링한다. 쉼·문장 끝으로 자른 발화를 단어 경계 양쪽 1.5초의 목소리가 다르면(유사도 0.2 미만) 더 자르고, 1초 이상 발화를 평균 연결로 묶는다(유사도 0.3). 서버 diarization이 7~141초 걸리던 것을 4~17초 CPU로 바꾼다. 모델을 못 읽으면 서버 diarization으로 돌아간다.
- **첫 패스가 오면 바로 리뷰**: 첫 패스를 먼저 보내고, 목소리 라벨을 붙인 뒤 리뷰를 시작해 나머지 패스와 겹친다. 이름은 시간으로 합친 결과에 얹는다.
- **텍스트 검토 끔**(`TEXT_MAX_SECONDS = 0`): 4패스 다수결 위에서 터널 WER을 0.196 → 0.200으로 올렸고 114초 걸렸다. 모든 클립에서 화자만 low thinking으로 묻는다.
- **리뷰 답 형식**: 발화마다 `"u12 이름"` 문자열 하나. 239발화 클립에서 답 토큰이 6,383 → 2,576개다.
- **다운로드 분리**: 오디오만 먼저 받고(약 6초) 바로 STT를 시작한다. 리뷰용 영상은 360p(DASH, 낮은 비트레이트 오디오)로 병렬로 받는다. 거부(403)되면 이전 형식으로, 그것도 실패하면 음성으로 리뷰한다.
- **목소리 임베딩 병렬화**: 5분 클립 3.5초 → 2.1초.
- **재시도**: 서버 503은 5초 간격으로 30번까지 다시 보낸다(이전 10초 간격 3번). GPU 메모리 부족 503은 기다리지 않고 바로 다시 보낸다. 오디오 다운로드가 거부(403)되면 두 번 더 시도한다.
