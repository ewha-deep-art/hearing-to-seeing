# 전사·화자 실험 기록 (2026-10-13 ~ 10-18)

[README.md](README.md)의 지표로 잰 실험이다. 채택한 설정과 결과는 README 4·5절에 있다.

## 1. 화자 임베딩 모델 (CPU)

gold 발화(1초 이상) 기준이다. NN은 최근접 이웃 발화가 같은 화자인 비율, AUC는 같은 화자 쌍과 다른 화자 쌍을 유사도로 가르는 정도다. 폴백 병합은 baseline 6개에 라벨 병합을 적용한 결과이고, 재배정은 리뷰 결과(검사·슬의)에 적용한 결과다.

| 모델 | NN | AUC | 폴백 병합 acc / F1 | 재배정 acc | 클립당 CPU |
|---|---|---|---|---|---|
| **WeSpeaker ResNet34 (채택)** | 0.874 | 0.876 | 0.764 / 0.488 | 0.901 | 5.7초 |
| WeSpeaker ResNet221 | 0.880 | 0.900 | 0.764 / 0.488 | 0.903 | 44초 |
| WeSpeaker ResNet293 | 0.895 | 0.892 | – | – | 47초 |
| WeSpeaker CN-Celeb ResNet34 | 0.874 | 0.877 | – | – | 9.0초 |
| 3D-Speaker CAM++ | 0.889 | 0.866 | 0.786 / 0.468 | 0.902 | 5.0초 |
| 3D-Speaker ERes2NetV2 | 0.871 | 0.884 | 0.722 / 0.420 | – | 19.7초 |
| ResNet34 + CAM++ 결합 | – | – | 0.785 / 0.481 | 0.903 | 약 11초 |

- 모델 간 차이가 작다. 남은 화자 오류는 목소리 비교로 갈리지 않는 종류여서, 가장 빠른 ResNet34를 유지했다.
- 임계값은 병합 0.50~0.70, 재배정 여유 0.05~0.20을 훑어 정했다.
- 리뷰가 '손님3'으로 묶은 화자를 목소리로 다시 나누는 방법도 시험했다. 대상은 슬의의 사비와 다른 조연이었고, 중심 유사도가 0.53으로 가까워 나뉘지 않았다.

## 2. VAD 임계값 (GPU)

| 설정 | 평균 WER | 평균 CER | 평균 D | IER |
|---|---|---|---|---|
| 기존 5패스 | 0.170 | 0.104 | 45.5 | 0.011 |
| 패스 0을 저-VAD(0.2/0.15)로 교체 (터널) | 0.237 → 0.258 | – | 74 → 76 | – |
| 저-VAD(0.35/0.25) 패스 추가 | 0.159 | 0.096 | 40.5 | 0.010 |
| **저-VAD(0.2/0.15) 패스 추가 (채택)** | 0.158 | 0.095 | 39.3 | 0.011 |

- 교체는 나빠진다. 첫 패스가 다수결에서 우선권(`PRIMARY_BIAS`)을 갖기 때문이다.
- 0.2 단독 패스는 반복 루프("이 새끼" × 7)를 만들기도 했다. 다수결과 루프 제거를 거치면 IER은 늘지 않았다.

## 3. diarization 모델 교체 (GPU), 진행 불가

- 서버 기본값은 이미 `pyannote/speaker-diarization-3.1`이다. 같은 180초 구간에서 단어 232개의 라벨이 3.1을 지정했을 때와 완전히 같았다.
- `pyannote/speaker-diarization-community-1`은 gated 모델이라 서버에서 쓸 수 없다. 서버에서 HuggingFace 이용 약관에 동의해야 열린다.

## 4. 원인 분석

- 삭제의 다수는 3단어 이상 연속 구간, 즉 한 줄이 통째로 빠진 것이다. 터널은 74개 중 44개, 검사외전은 59개 중 43개다.
- 발화 단위(라벨 변화, 0.5초 쉼, 문장 끝으로 자른 단위)의 화자 순도는 98~99.9%다. 발화마다 이름만 맞게 붙이면 정확도 상한은 충분하다.

## 5. 설정 비교

- 목소리 재배정 끄고 켜기(10-18 리뷰 결과 캐시): 슬의 정확도 0.873 → 0.934, 브레드 0.899 → 0.906, 터널 0.983 그대로.
- 직전 설정(`gemini-3.5-flash` 리뷰, 단역을 '손님N'으로 부르는 프롬프트, 실패 시 3.8·3.7)과 비교하면 평균 정확도 0.928 → 0.932, macro F1 0.785 → 0.799다. 슬의(0.774 → 0.825)와 브레드(0.716 → 0.792)가 올랐고, 부부(0.895 → 0.857)와 터널(0.761 → 0.736)은 내렸다. 리뷰는 같은 설정에서도 실행마다 달라지므로 영상별 차이는 이 범위 안에서 흔들린다.
- 목소리 재배정 여유(0.05~0.20)와 최소 길이(0.5~2초)를 직전 리뷰 결과로 다시 훑었다. 평균 정확도 차이가 0.01 미만이라 기존 값을 유지했다.

## 6. 처리 시간 단축 (2026-10-18)

결과와 채택한 설정은 README 4.3·5.8절에 있다.

### 6.1 어디서 시간이 드는가

이전 파이프라인으로 터널(280초)을 쟀다. 다운로드 15초를 빼고 200초였다.

| 단계 | 시간 |
|---|---|
| STT 6패스 (차례대로) | 130초 |
| 영상 리뷰 (텍스트 검토, 전체 thinking) | 59초 |
| 목소리 보정 | 9초 |

- 서버 응답의 `timings`로 본 패스별 계산 시간(슬의 581초): large-v3/30은 전사 12.6초, 정렬 5.7초, diarization 14.2초다. chunk 5 패스는 전사만 33초다(30초 창 하나에 5초씩 채워 6배 계산). turbo/30은 전사 6.4초다.
- 패스마다 오디오를 다시 올린다. 업로드는 약 1.3~1.5 MB/s다. 터널 WAV(8.9MB)는 패스당 5.6초, FLAC(4.7MB)은 3.5초가 계산 외 시간이다. FLAC은 결과 단어가 WAV와 같다.
- diarization 시간은 실행마다 크게 다르다. 검사외전 141·24·132초, 브레드이발소 76·127·73초, 부부의 세계 17·37초, 슬의 14초, 터널 7초. 서버를 다른 사용자와 같이 쓴다.

### 6.2 패스 조합 (GPU 캐시 후 오프라인)

7개 후보 패스를 6개 영상에서 한 번씩 디코딩해 두고, diarization 패스(large-v3/30)를 첫 패스로 고정한 64개 조합의 다수결을 쟀다. 리뷰 없는 텍스트 지표다. 비용은 패스별 전사+정렬 시간의 클립 평균 합(초)이다.

| 조합 | 평균 WER | 평균 CER | 비용 |
|---|---|---|---|
| 이전 6패스 (v3/30, v2/30, v2/20, v3/5, turbo/5, v3/30 저-VAD) | 0.158 | 0.095 | 125 |
| 후보 7개 전부 | 0.159 | 0.096 | 136 |
| large-v3/30 하나 | 0.151 | 0.090 | 16 |
| v3/30 + v3/30 저-VAD + turbo/30 (**10분 초과 채택**) | 0.153 | 0.091 | 44 |
| v3/30 + v3/30 저-VAD + v2/30 + turbo/30 (**채택**) | **0.149** | **0.089** | 60 |

- 4패스는 6개 영상 모두에서 이전 6패스보다 WER이 낮다(브레드 0.112 → 0.095, 부부 0.088 → 0.079, 슬의 0.129 → 0.125, 검사 0.251 → 0.241, 터널 0.207 → 0.196, 마녀 0.162 → 0.157).
- 패스 2개는 1개와 결과가 같다. 다수결은 3개부터 돈다.
- 한 패스만 쓰면 루프 대비와 리뷰용 엇갈린 자리가 없어져 채택하지 않았다.

### 6.3 업로드 크기

4패스를 같은 설정으로 다시 디코딩해 비교했다(리뷰 없음).

| 업로드 | 터널 크기 | 평균 WER | 평균 화자 acc |
|---|---|---|---|
| FLAC (채택) | 4.7MB | 0.149 | 0.759 |
| Opus 64k | 2.4MB | 0.153 | 0.803 |
| Opus 32k (5개 영상) | 1.1MB | 0.169 (FLAC 0.148) | 0.776 |

- 32k는 5개 모두 WER이 올랐고, 64k는 6개 중 3개가 올랐다. 무손실인 FLAC을 쓴다.

### 6.4 서버 요청 방식

- **동시 요청**: 두 번째 요청은 거절되지 않고 기다린다. 하지만 서버는 앞 요청이 끝나야 다음 요청 본문을 읽는다. 앞 패스가 도는 동안 다음 패스를 미리 보내도 마녀에서 패스 사이 간격이 7.8초로, 차례대로 보낼 때와 같았다. 되돌렸다. 업로드 두 개를 동시에 시작하면 503이 나기도 했다.
- **`batch_size` 32**: 기본값 8보다 터널에서 전사 7.8 → 6.3초였지만 단어 수가 373 → 368로 바뀌었다. 슬의에서는 전사가 12.6 → 81.7초로 느려졌다(8GB 카드 메모리 부족으로 추정). 기본값을 유지한다.
- **GPU 메모리 부족**: 873초 클립의 large-v3 패스가 30초쯤 뒤 503(`CUDA failed with error out of memory`)으로 실패하고, 바로 다시 보내면 성공했다. 웹 작업 단계로 3번 돌려 3번 모두 첫 패스에서 났다. 모델 전환과는 상관이 없었다(turbo 다음 large-v3 긴 요청은 성공, 짧은 요청으로 미리 전환한 뒤 긴 요청은 실패). 서버가 권하는 `batch_size` 4는 쓰지 않았다. 배치 크기를 바꾸면 결과 단어가 달라진다(16·32에서 확인).
- **로드된 모델 먼저 보내기**(`_pass_order`) 대신 diarization 패스를 항상 먼저 보낸다. 리뷰가 그 결과로 시작하기 때문이다. 모델 전환은 2~4초다.

### 6.5 리뷰

- **지연 구성**: 슬의(581초, 화자만)를 스트리밍으로 재면 첫 토큰까지 31초(영상 60k 토큰 처리 + 대기), 답 2,560토큰 생성 10초였다. 같은 호출이 대기 때문에 140초 걸린 적도 있다.
- **답 형식**: `{"id", "speaker"}` 객체 대신 `"u12 이름"` 문자열로 바꿔 답 토큰이 6,383 → 2,576개다. 모든 발화에 이름이 붙었다.
- **텍스트 검토**: 4패스 캐시 위에서 터널에 텍스트 검토를 돌리면 13곳을 고쳐 WER 0.196 → 0.200이 됐다. thinking 8,026토큰, 114초였다. 껐다.
- **첫 패스로 리뷰**: 같은 답(슬의)을 4패스 합친 결과에 시간으로 얹으면 0.944, 첫 패스에만 얹으면 0.941이다. 이름을 얹는 방식으로는 손해가 없다. 단어 겹침으로 옮기는 방식도 0.944로 같았다.
- **이전·현재 방식 짝 비교** (`gemini-3.8-flash`, 캐시 입력, 목소리 보정 포함). 이전은 6패스 합친 대사 + 객체 답, 현재는 첫 패스 대사 + 문자열 답 + 4패스에 얹기다.

| 영상 | 이전 | 현재 |
|---|---|---|
| 터널 | 0.980 | 0.973 |
| 검사외전 | 0.932 | 0.922 |
| 슬기로운 의사생활 | 0.915 | 0.866 |
| 부부의 세계 | 0.924 | 0.913 |
| 마녀 | 0.867 | 0.883 |
| 브레드이발소 | (503) | 0.915 |
| **평균 (5개)** | 0.924 | 0.911 |

- 같은 방식의 실행 간 편차가 한 영상에서 0.08까지 난다(슬의 0.866·0.944, 검사 0.751·0.922). 검사외전 0.751 실행은 주연 한치원의 발화 91단어를 이진석으로 불렀다.

### 6.6 다운로드

- 이전 1080p 다운로드는 14~30초, Gemini 업로드는 34~54초였다.
- 오디오만 받으면 약 6초다.
- 360p는 progressive 형식(18)이 고르기 쉬운데 24~159초로 들쭉날쭉했다. `bv*`가 오디오 포함 형식을 고르기 때문이라 `bv`(영상만)로 바꿨다. 360p DASH는 7~30초였고 403으로 거부되기도 했다.
- yt-dlp 정보(`youtube_info`)를 다시 써서 추출을 건너뛰면 403이 난다.

### 6.7 목소리 화자 분리 (채택)

서버 diarization 대신 첫 패스 발화의 목소리 임베딩(WeSpeaker ResNet34)으로 라벨을 붙인다. 리뷰 없는 경로(목소리 병합 포함) 평균 정확도로 골랐다. 서버 diarization은 0.759다.

| 설정 | 평균 acc | 비고 |
|---|---|---|
| 발화(0.5초 쉼·문장 끝) 전부 묶기, 유사도 0.25 | 0.763 | 화자 8~46명으로 쪼개짐 |
| 1초 이상만 묶기(0.3), 짧은 발화는 가까운 중심에 | 0.780 | 마녀 0.705, 부부 0.877로 서버보다 낮음 |
| + Whisper 세그먼트 경계에서도 자르기 | 0.777 | 세그먼트가 이미 문장 끝에서 끊김 |
| + 단어 경계 양쪽 1.5초 목소리 유사도 0.2 미만에서 자르기 (**채택**) | 0.797 | 브레드 0.651 → 0.743. 0.15·0.25에서 0.789·0.776 |
| 구현(`voice.diarize`)으로 다시 잼 | 0.804 | 4~17초 CPU |

리뷰 경로 (`gemini-3.8-flash`, 짝 비교 6.5절과 같은 조건):

| 영상 | 이전 방식 | 서버 라벨 | 목소리 라벨 |
|---|---|---|---|
| 터널 | 0.980 | 0.973 | 0.973 |
| 검사외전 | 0.932 | 0.922 | 0.922 |
| 슬기로운 의사생활 | 0.915 | 0.866 | 0.913 |
| 마녀 | 0.867 | 0.883 | 0.883 |
| 브레드이발소 | (503) | 0.915 | 0.891 |
| 부부의 세계 | 0.924 | 0.913 | (503) |

- 브레드이발소는 변화 지점 자르기 전에 0.808이었다. 발화가 227개(서버 라벨) 대신 181개로 묶여 빠른 주고받기가 한 발화에 섞였다. 자른 뒤 213개, 0.891이다.
- 웹 작업과 같은 단계로 돌린 검사외전(`gemini-3.7-flash` 리뷰)은 0.918, 처리 시간 251.7초 → 113.1초다.
